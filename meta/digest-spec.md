# 日报规范

## 公开安全（必读）

本仓与 Pages **公开可读**。写入 `digests/`、`meta/`、README 时遵守：

**禁止写入公开文件**
- 密钥、token、cookie、`.env`、私钥、API 额度 / credits / 账单
- 未公开的实验数字、内部评审意见、未发表手稿全文、私人通信
- 个人敏感信息（手机、私人邮箱、住址、证件号等）
- 平台内部工具名、agent/自动化内部 ID、本机绝对路径（接管文档用角色与意图描述即可）
- 检索过程备注（「非本窗口」、`max_results`、tool 名等）

**允许写入**
- 已公开学术身份与实验室归属（以 blog / academic / 个人主页为准）
- 公开论文、开源仓库、会议录用等公开事实
- 研究方向与课题焦点的**公开表述**（如 Real→Sim→Real、可重光照 3DGS），勿写未公开的具体实验配置或未披露结果

拿不准：默认不写进公开仓；可只在与用户的私聊里说明。

## 成稿形态（完整版）
- 今日速览 / 总体总结：有判断、点名必读；文笔自然，像研究笔记
- 主题分块用自然语言标题（如「逆渲染与材质」「正向渲染效率」「可编辑动态资产与绑定」「具身数据增强与回环」）
- 正文**不要**标注 `[A]` / `[B]` / `[C]`（内部按 `research-interests.md` 最新主线加权）



## 写作前检查长期记忆（每日必做）
动笔写当日日报**之前**必须：
1. 阅读并核对 `meta/LONG_TERM_MEMORY.md`、`digest-spec.md`、`research-interests.md`、`interest-notes.md`、`failover.json`、`privacy.md`、`seen-papers.json`
2. 对照 `interest-notes.md` 与 `rubatotree/notes` / `blog` / `academic` 近期 commits 与相关正文（notes 与 blog 同等重点，所有 Bot 按 `research-interests.md` 的联合校准规则执行）：若兴趣、规范、故障转移名册或流程有变，**先更新**相应 `meta/` 文档并提交，再写日报；随手笔记中的 active 条目可进入「新兴趣相关」做前沿扫描（勿压过主课题）；Cream 会在每日 05:00 HKT 把当天讨论摘要写入 `interest-notes.md`
3. 无变更则不必空改；有变更须写进公开记忆（遵守 `privacy.md`），避免只改私聊、仓内过时

## 协同 Bot 文风学习（必做）
加入协同维护的 Bot，在撰写**当日**日报前必须：
1. 打开近几天（建议至少 **3** 篇）`digests/`，优先读 **编写署名不是自己** 的篇目
2. 学习基本写法与优点：今日速览的判断力与结构、分块小结、方法概要/值得关注的信息密度、锚点与标题栏（短名 · Venue · 日期）、覆盖说明与署名习惯
3. **允许**在清晰前提下做风格创新，不必逐句模仿
4. **目标：** 尽可能清晰易读；概括与重点分明（必读先点名、原因一句说清）；避免流水账与空话

主责 Bot 亦应定期回看他人接管稿，吸收优点并保持规范字段完整。

## 论文标题栏（目录可见）

三级标题格式（会进入站点 TOC）：

```text
### 短名 · Venue或arXiv · YYYY-MM-DD
```

示例：
- `### LightBridge · arXiv · 2026-09-02`
- `### UniMate · SIGGRAPH Asia 2026 · 2026-09-04`
- `### TileGS · Pacific Graphics 2026 / CGF · 2026-09-03`

规则：
- 已接收会议/期刊：写正式 venue 名 + arXiv 挂出日（或正式发表日，若已知且更准）
- 仅预印本：`arXiv · 首次挂出日`
- 标题上方保留稳定锚点：`<a id="slug"></a>`
- 正文仍保留完整 **发表时间** / **投稿信息** 字段，供细读；TOC 靠标题栏一眼看到会议与时间
- 圈内动态等非论文小节（媒体 / X / Ke-Sen 等）不要硬套「· Venue · 日期」

## 每篇必含字段
1. 一句话判断要点（标题下首段）
2. Title（英文全名）
3. 作者（英文 / 拼音，不译成中文姓名）
4. 单位（仅确定国内机构用中文；不确定保留原文）
5. 投稿信息（已接收 / 推测+依据 / 未标明；禁止把推测写成已中）
6. 发表时间（预印本：arXiv 首次挂出日；已发表：会议/期刊时间）
7. arXiv abs / PDF（或其它稳定入口）
8. 摘要中译
9. **方法与原理**（基于全文 / HTML，讲清输入、处理步骤、模块间的数据流、设计理由和输出；不能只列模块名，详见下节）
10. **值得关注**（相对公开研究方向的对照阅读建议；勿泄露未公开实验）
11. 相关链接（主页 / 代码 / 视频；找不到如实写）
12. 配图嵌入正文（优先论文原有 pipeline；必读至少 1 张，详见下节）

## 配图优先级（2026-09-23）

论文含 pipeline（方法流程）图时，优先展示原论文 pipeline 图并附图号与来源链接；只有论文没有 pipeline 图，或原图不够清晰、确有必要改善原理展示时，才补充自绘示意图。自绘图尽量使用中文标注，必要的模型名、缩写和公式保留原文；标明「据论文整理的示意图」及依据，不冒充原图。

原图配中文图注解释关键步骤与数据流；teaser 或效果图可补充结果展示，不能代替已有的方法流程图。自绘图仅依据公开论文或项目资料，不加入未公开实验或未经核实的模块。

## 可读性与方法讲解（2026-09-22 起执行）

读者有图形学、数学与编程基础，但不预设熟悉每篇论文及具身、强化学习、LLM 的专门术语。目标是读完能复述方法为何有效；不要用降低技术深度来换取表面的简短。

### 名词必须在使用处讲明白

- 每期独立可读。陌生缩写首次出现时写「中文含义 + 缩写 + 在本文中的作用」；只补英文全称不算解释。例如「监督微调（SFT）：用成功示教中的观测—动作配对训练策略」。后文沿用同一称呼。
- 论文名、模型名、数据集名先给身份和用途，例如「π₀.₅ 是这里被微调的机器人动作策略」，不能假设名字本身传递了方法。无法核实的名字不要补造全称。
- 中文术语同样需要解释：特权状态、残差、蒸馏、闭环、域差异等，应就地说明其操作含义。摘要中已出现的词不能等到方法末尾才定义。
- 速览以具体问题和动作写结论，避免缩写和英文名连缀。非必要英文改成中文；不要在一句话内引入多个未解释概念。通用基础词不反复科普，难点可加一两句背景；不要把全部解释堆进文末词表。

### 每篇形成完整的方法因果链

按内容组织自然段或步骤，不必机械套用所有小标题，但必须回答：

1. **问题与已有方法的瓶颈：** 到底哪一步做不好？为什么原有做法会失败？
2. **输入、输出与前提：** 接收什么观测、资产、状态或示教；最终得到模型、动作、数据还是资产；哪些信息需要人、传感器或仿真器额外提供。
3. **怎样做：** 用 3–5 个有先后关系的步骤讲关键模块；每步说明接收什么、做什么、交给下一步什么。不能只写「结合 X 与 Y」。
4. **为什么这样做：** 指出设计解决了什么困难，和最简单基线相比改变在哪里。作者解释、编辑推理、实验支持分开标明；不能把直觉说成已证明的因果关系。
5. **怎样学习和使用：** 有学习模块时交代监督/奖励来源、预测对象或损失、被优化的参数，以及部署时保留哪些模块、拿不到哪些训练期信息。优化、规划或非学习方法则说明目标与求解方式，不强套训练术语。

重点论文默认用数个完整段落讲透；可附一条核心公式，逐一解释符号、每项作用和公式在流程中的位置。只有在表达关系确实更清楚时才加图或输入输出表，图后必须解读。类比或简化例子注明为帮助理解，不冒充论文实验；代码可读时可指向关键实现，但不把未经核实的实现猜测写成事实。

公式用 `\(…\)` 或 `$…$` 写行内数学，用单独成行的 `\[…\]` 或 `$$…$$` 写展示公式；前后留空行。变量也要使用数学定界符，不能写成 `(H_j)` 这样的普通括号。发布前在网页正文检查行内和展示公式都已排版，LaTeX 命令没有作为原样文本显示；代码围栏与行内代码中的公式保持代码样式。

**结果与局限后置且具体：** 先让读者理解方法，再集中给实验结果、比较条件、成本和未验证环节。指标首次出现时解释怎样算、越大还是越小越好；区分覆盖任务数、平均成功率、完成比例，说明加速的计时范围。避免每段都用同一句证据警告打断讲解。

**全文依据与篇幅取舍：** 必读论文须阅读方法及关键实验；来源不足时明确「仅摘要可核实」，降为简讯或暂缓，不编造网络、损失或流程。选读也须有最小完整因果链。篇幅或时间不足时减少收录数量和重复评论，优先保留方法解释。新闻至少说明新产品/模型是什么、做什么；公开资料未披露内部原理时如实说，不用宣传名词补全机制。

- [ ] 不打开原文，能否说出每篇的输入、输出及关键步骤？

- [ ] 是否区分训练/数据生成时的信息与部署时的输入？

## 圈内新闻与社区反应（每日必检）
在论文策展之外，每日主动检索 **LLM、Agent、图形学、具身智能** 四个领域的新闻与社区反应；不限于与 PTIR-GS / Real2Sim 直接相关的事件。关注模型与产品发布、开源与重要版本更新、开发工具和工作流、评测与复现、会议与行业重大动态。论文主线继续按研究兴趣加权。

设置独立「圈内新闻与社区反应」栏目，按重要性精选，通常 3–6 条，可少于此数；四领域都要检查，但不强求每天各占一条。保持分层阅读，重大新闻可进入置顶速览，其余短写，避免挤占重点论文篇幅。

每条用短段落写清：
1. **发生了什么**：事件、主体、发生/发布日期及原始来源；优先核实官方公告、发布说明、仓库或作者原文，厂商自报的能力/指标须明确归因。
2. **社区如何反应**：实际使用与复现反馈、认可点、质疑点或分歧；给出可回溯的原帖/讨论链接及日期，说明是谁、在哪个社区提出。可检索 X、Hacker News、Reddit、GitHub Issues/Discussions、Hugging Face 讨论及中文技术社区；媒体转述与作者宣传不能冒充独立社区反馈。
3. **为什么值得关注**：用一句具体判断解释影响；将编辑判断与已核实事实、社区观点分开，不必强行关联主课题。

有足够材料时选取不同立场或独立使用者的反馈；不为凑对立而制造争议，不把少数帖子概括为「社区共识」，不以点赞量证明技术结论。没有可靠反馈时写「暂未找到可核实的社区反馈」，不编造情绪或引述；未核实传闻不得当作事实。

新闻以内容覆盖日为主；跨日事件只有出现实质新进展或新反馈才重提，说明事件原日期与本次更新日期。检查近期日报去重，新闻不混入仅存论文元数据的 seen-papers.json。确无高信号时简述；来源无法访问或覆盖不足应在覆盖说明中如实交代，不把未检索到等同于无新闻。过程日志与额度不入库。

## 日期约定
- **日报日期**（文件名 `digests/YYYY-MM-DD.md`、站点选日）= **发布日**（通常为早上 5:30 HKT）
- **内容覆盖** = **前一自然日**的新内容（例如 9 月 7 日日报写 9 月 6 日新稿）
- 文末「覆盖说明」同时写明日报日期与内容覆盖日；周末等无独立 arXiv 公告时，可纳入相邻公告日积压，但发布日仍用当日
- `digests/index.json` 条目建议含 `content_day`
- 每期在 `digests/index.json` 同时填写 `subtitle`：概括当天最重要的研究线索，尽量控制在 6–16 个汉字（英文缩写按显示宽度酌情缩短）；时间轴在日期下方显示这个短标题。`title` 可保留较详细的内容概述。短标题应与正文吻合，不堆砌论文名，不把尚未验证的效果写成事实。

## 故障说明（故障转移接管时必写）
当且仅当本篇是因**先前顺位 Bot 失效／超时未发布**而由更后顺位 standby（或等价接管者）写就并推送时，必须在全文**最下方**（紧接 `**编写：**` 行之后）追加简短 **故障说明**，例如：

```markdown
**故障说明：** 本日由 Cream 于 06:05 HKT 故障转移接管发布。先前顺位未在窗口内成功出稿：Neon（05:30–06:00）无当日 digest。依据 `meta/failover.json` 当日 `failover`／`claim` 事件。
```

约定：
- **触发：** failover 检查判定今日缺稿，且 CAS claim 成功后的那次发布；正常 primary 按时发布**不要**写故障说明
- **位置：** 整篇日报最底部（在 `**编写：**` 之后），便于人工扫一眼看出是否接管稿
- **内容须含：** 接管 Bot 代号与大致时间；失效／未完成的前序顺位（代号 + 窗口或检查时刻）；可核验依据（如缺 `digests/当日.md`、无有效 `last_success`、无有效 claim 等）——只写公开可核验事实
- **禁止：** 密钥、额度、内部 tool／路径、未公开私聊；不要揣测「Bot 崩溃原因」除非仓内已有公开 `fail` 事件可引用
- 同步在 `failover.json` 写入对应 `failover`（及必要时 `fail`）事件；私聊维护者的检查报告亦应复述同一故障摘要

## Git 提交署名
向 `rubatotree/research-daily` 提交时，若维护 Bot 有公开代号，须在 **commit message 的 description（正文，非仅 subject 一行）** 中署名，例如：

```text
Require viewpoint distillation for community digests

Rewrite 圈内 with fact/viewpoint/contrast; update specs.

编写：Cream
```

或单独一行 `Signed-off-by-bot: Cream` / `Bot: Cream`。日报文末 `**编写：**` 与 commit description 署名应一致（同一次发布）。无代号的人类提交可省略。
